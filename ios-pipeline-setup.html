Flutter · Jenkins · iOS release

Two Macs, One Pipeline

Everything you must do, in order, to make this repository build the app and send it to TestFlight — without anyone logging into Xcode on the build machine. Written for two computers: the Development Mac you work on, and the Pipeline Mac that runs Jenkins.

What we are building, in plain words

One Jenkins job. You pick Android or iOS, type the version and build number, press Build. The job gets the code, gets the secret files, builds the app, and sends it to the store. Nobody types an Apple password anywhere.

The two Macs

Development Mac

The Mac you work on

It has Xcode open, a keychain with your certificates, and a human at the keyboard. You use it once, to collect the signing files. After that you never need it for the pipeline again.

Pipeline Mac

The Mac that builds

It runs the Jenkins agent. It has Xcode installed but never logs into an Apple account. Every build brings its own certificate and profile, uses them, and deletes them.

The five things iOS signing needs

Logging into Xcode gives you all five by hand. We replace each one with something a script can use.

ThingWhere it comes fromHow often
dist.p12Exported from the Development Mac keychainOnce a year (it expires)
p12 passwordYou choose it during exportOnce a year
AuthKey.p8App Store Connect → API keyOnce ever
Key ID + Issuer IDSame page as the .p8Once ever
Provisioning profileDownloaded from Apple every buildNever touch it again
The whole idea

The profile is the part that expires fastest, so the build downloads a fresh one each time. The certificate cannot be re-made each build — Apple allows only two or three — so it is stored once and treated like a password.

Order of work

  • Tab 01 — Development Mac. Collect the signing files. About 30 minutes, once ever.
  • Tab 02 — Pipeline Mac. Install the tools and the agent. About 45 minutes, once ever.
  • Tab 03 — Jenkins. Add credentials and the job. About 15 minutes.

Development Mac

Collect the signing files

Do all of this on the Mac where you normally open Xcode. You do it one time. Every future project reuses the same files.

  1. Check if you already have a distribution certificate

    Open Terminal and run this. It lists the signing identities in your keychain.

    If you see a line with Apple Distribution: Your Company (TEAMID), go to step 2.

    If nothing prints, someone in your team has it, or nobody made one yet. Ask first. If nobody has one: open Xcode → Settings → Accounts → select the team → Manage Certificates → + → Apple Distribution.

    Careful

    Apple allows only two or three distribution certificates per account. Do not create a new one just because you cannot find the old one — you can lock the whole team out. Ask a teammate for their .p12 instead.

  2. Create an App Store Connect API key

    In a browser · appstoreconnect.apple.com

    Go to Users and Access → Integrations → App Store Connect API and press the + button. Name it CI Pipeline and set the role to App Manager.

    Write down three things from that page:

    • Issuer ID — the long id at the top of the page, looks like 69a6de7e-1234-4c5b-8f21-9a0bcdef1234
    • Key ID — the short id in the row, looks like 2X9R4HXF34
    • The .p8 file — press Download
    One chance only

    The .p8 file downloads exactly once. If you lose it you must revoke the key and make a new one. Save it somewhere safe before you close the page.

  3. Export the certificate as a .p12 file

    Keychain Access app

    This is the last time you use a window with buttons for signing.

    • Open Keychain Access
    • Click My Certificates in the sidebar
    • Find Apple Distribution: Your Company (TEAMID)
    • Click the small arrow next to it. You must see a private key underneath. If there is no key, this Mac cannot export it.
    • Right click the certificate → Export
    • Format: Personal Information Exchange (.p12)
    • Save as dist.p12 and set a password

    Write that password down. You will paste it into Jenkins in step 7.

  4. Create the provisioning profile in Apple's portal

    In a browser · developer.apple.com

    • Go to Certificates, Identifiers & Profiles → Profiles
    • Press +
    • Choose App Store Connect under Distribution
    • Pick your App ID (the bundle id of the app)
    • Pick the certificate from step 3
    • Give it a clear name, for example CM App AppStore, and generate it
    Do not download it

    The profile only needs to exist. From now on the build downloads it from Apple every time, so it can never go stale.

  5. Find the bundle id and the Team ID

    Run this inside the Flutter app repository (not this pipeline repository):

    The Team ID is the 10 character code on developer.apple.com → Membership, and it is also inside the brackets of your certificate name.

  6. Put the two files into your S3 / R2 bucket

    This repository already downloads secret files from object storage — the keystore, the plists. The .p8 and the .p12 are the same kind of thing, so they go to the same place. No base64, no new plumbing.

    Use the same bucket and the same endpoint that is already in pipeline.properties.

  7. Add the p12 password to Jenkins

    In a browser · your Jenkins

    Manage Jenkins → Credentials → add a Secret text credential. ID: ios-p12-password. Value: the password from step 3.

    That is the only new credential you need. The Key ID and Issuer ID are not secrets — they go into pipeline.properties (see tab 04).

  8. Clean up and set one reminder

    Then put one entry in your calendar, eleven months from today: "re-export dist.p12, upload it again". That is the only manual work left, forever.

Pipeline Mac

Set up the build machine

A fresh Mac to a working Jenkins agent. Do these in order. Nothing here involves an Apple account.

  1. Make a real user account and log in on the screen

    Create a normal user, for example builder. Log in on the physical screen at least once, not only over SSH. macOS keychains behave differently without a real login session, and that is the number one cause of builds that work in a terminal but fail in Jenkins.

    Turn on automatic login: System Settings → Users & Groups → Automatically log in as → builder. Then stop the machine sleeping:

  2. Install Xcode and accept the licence

    Install Xcode from the App Store. Open it once so it finishes installing its components, then close it. Now run these:

    Do not sign in

    When Xcode asks for an Apple ID, close the window. This Mac must never have an Apple account. Every build brings its own certificate and deletes it afterwards.

  3. Install Homebrew

    The pipeline installs fvm, infisical and aws by itself if they are missing — but only if Homebrew exists. So Homebrew is not optional.

  4. Install the tools the pipeline cannot install for you
    Why CocoaPods

    flutter build ios runs pod install underneath. CocoaPods does not ship with macOS, and the pipeline does not install it, so put it on the machine now.

  5. Check the built-in tools are there

    These five come with macOS and Xcode. The build uses nothing else for signing.

  6. Create the node in Jenkins and download the agent

    In a browser · your Jenkins

    • Manage Jenkins → Nodes → New Node
    • Name: mac-pipeline
    • Labels: macos — this must match agent { label 'macos' } in the Jenkinsfile
    • Remote root directory: /Users/builder/jenkins-agent
    • Launch method: Launch agent by connecting it to the controller
    • Save, open the node page, and copy the agent.jar download link and the secret
  7. Start the agent as your logged-in user

    Create this file at ~/Library/LaunchAgents/com.jenkins.agent.plist:

    The most common mistake

    Put the file in ~/Library/LaunchAgents — a LaunchAgent, which runs as you. Never in /Library/LaunchDaemons. A daemon has no user session, and signing will fail in ways that are very hard to read. Also: PATH must include /opt/homebrew/bin, or the build will not find brew, fvm or pod.

  8. Put this pipeline repository on the machine

    The Jenkinsfile reads its settings from an absolute path on the agent:

    So clone this repository on the Pipeline Mac and make the path match — or change that line to the Pipeline Mac's path. Both work; pick one and keep it.

  9. Open the network

    The Pipeline Mac must reach these on port 443:

    • api.appstoreconnect.apple.com — the profile is downloaded every build
    • *.r2.cloudflarestorage.com — or whatever your S3 endpoint is
    • app.infisical.com — for the .env file
    • gitlab.webelight.co.in — the code
    • Apple's upload servers, for TestFlight

    If you clone over SSH you also need port 22 to GitLab. Inside the office that is usually open, outside it usually is not — that is why GIT_PROTOCOL=https is the safer default.

Jenkins: credentials, node, job

The Jenkinsfile never holds a secret. It holds the name of a secret, and Jenkins hands the value over at build time.

Credentials to create

Manage Jenkins → Credentials → System → Global → Add Credentials. The ID on the left must match exactly what is written in pipeline.properties.

IDKindWhat goes in it
gitlab-tokenUsername with passwordUsername oauth2, password is the GitLab access token
infisical-tokenSecret textThe Infisical service token
shorebird-tokenSecret textThe Shorebird CI token
r2-credentialsUsername with passwordUsername is the Access Key ID, password is the Secret Access Key
ios-p12-passwordSecret textThe password you set when exporting dist.p12
Note

If you use GIT_PROTOCOL=ssh instead, gitlab-token must be an SSH Username with private key credential with username git. The kind must always match the protocol.

The node

One node, label macos, as created in tab 02. The Jenkinsfile starts with agent { label 'macos' }, so a wrong label means the job waits forever with no error.

The job

  • New Item → Pipeline → name it, for example flutter-release-pipeline
  • Pipeline → Definition: Pipeline script from SCM
  • SCM: Git → this repository → credentials → branch main
  • Script Path: Jenkinsfile
  • Save. Run it once — the first run fails or does nothing useful, but it registers the parameters

After that first run the build page shows the four parameters the Jenkinsfile declares: PLATFORM, BUILD_RUNNER, BUILD_VERSION, APP_BUILD_NUMBER.

What to add to this repository

Four changes: new settings, two script files, and one new stage in the Jenkinsfile. Write them here, commit, and the Pipeline Mac picks them up on the next pull.

1. New lines in pipeline.properties

2. ci/fetch_profile.py

Asks Apple for the provisioning profile and writes it into both folders Xcode looks in. Uses only Python and openssl, both already on the Mac.

3. ci/ios_build.sh

The whole iOS build. Six steps, then a cleanup that always runs. Note three things that are different from a generic script: it uses fvm flutter so the pinned SDK is used, it takes the .p12 and .p8 as files because the pipeline already downloads them, and it builds in APP_DIR because the app lives in the Jenkins workspace while this script lives in the pipeline repo.

4. The new stage in the Jenkinsfile

Add it after Load Secret Files. It only runs when the user picked iOS.

Why the script lives here and not in the app repo

The Jenkins job clones the app fresh every build. If the scripts lived in the app repo you would have to copy them into every project and keep them in sync. One copy in this repo, called by absolute path, serves every app.

The build commands

Every command the pipeline fires, and the same commands to run by hand when you want to see what is happening.

First: find your scheme and flavor

If the project has flavors, the scheme is usually not Runner. Check before you fill in pipeline.properties:

It prints the schemes and the build configurations. A project with a prod flavor usually has scheme prod and configuration Release-prod. The names in the output are the names you put in the settings file.

Flutter, with the pinned SDK

The pipeline pins Flutter with FVM, so always say fvm flutter, never plain flutter. Plain flutter uses whatever SDK happens to be on the machine, and the build silently differs from the pipeline.

iOS

Do not run pod install yourself

flutter build ios runs pod install for you. Running it again by hand only adds a minute to every build.

Android

Android signing needs android/key.properties and android/cm-app.jks — the pipeline already downloads both from storage before this step runs.

Shorebird (code push)

The job has a BUILD_RUNNER choice. Shorebird does its own build, so it replaces the Flutter commands rather than adding to them.

Shorebird reads the token from SHOREBIRD_TOKEN in the environment, which comes from the Jenkins credential named in pipeline.properties. The signing setup in this guide still applies to shorebird release ios — it archives with Xcode underneath.

Run the whole thing by hand

Keep DO_UPLOAD off at first

Run it two or three times with DO_UPLOAD=false. You get a real .ipa to look at, and you do not burn build numbers on App Store Connect. Each build number can be uploaded only once, ever.

The first run, in order

Do not wire everything up and press Build. Prove each layer works before adding the next one. When something breaks you then know exactly which layer did it.

  1. Prove the tools

    Pipeline Mac · a normal terminal, logged in as the agent user

    All five must print something. If any fails, go back to tab 02.

  2. Prove Apple answers

    Put the .p8 somewhere temporary and run only the profile downloader. This checks the API key, the Issuer ID, the bundle id and the profile all at once, in about two seconds.

    Success looks like: fetch_profile: using 'CM App AppStore' (uuid…)

  3. Prove the certificate

    You must see one line saying Apple Distribution. If you see Apple Development instead, you exported the wrong certificate.

  4. Run the full script by hand, no upload

    Use the block at the bottom of tab 05, with DO_UPLOAD=false. This is the run that finds most problems. Expect it to take 10–20 minutes the first time.

  5. Run it from Jenkins, no upload

    Now the same thing, triggered from the job. If step 4 worked and this does not, the problem is environment: PATH in the LaunchAgent plist, or the agent running as a daemon instead of as your user.

  6. Turn the upload on

    Tick DO_UPLOAD. Watch App Store Connect → your app → TestFlight → Activity. Processing takes 5 to 30 minutes after the upload finishes. An email arrives if Apple rejects the build.

What a good run looks like in the log

When it breaks

Almost every failure is one of these eight. The message on the left, the real cause on the right.

What you seeWhat it means and what to do
User interaction is not allowed The set-key-partition-list line did not run, or the keychain password did not match. macOS wants to show a password window and there is nobody to click it.
errSecInternalComponent Same cause, different words. Check the partition list line and that the keychain is unlocked.
No signing certificate "iOS Distribution" found The certificate went into one keychain and xcodebuild looked in another. Run security find-identity -v -p codesigning to see what is actually visible.
no ACTIVE profile found for <bundle id> The profile does not exist, or its type is different. Create it once in the portal, and check that IOS_PROFILE_TYPE matches what you made.
exportArchive failed, no useful message Nearly always an incomplete ExportOptions.plist. On Xcode 15 or older set IOS_EXPORT_METHOD=app-store instead of app-store-connect.
Works over SSH, fails from Jenkins The agent is a LaunchDaemon with no user session, or its PATH is missing /opt/homebrew/bin. Fix the plist, then launchctl unload and load -w it again.
The build number has already been used Every upload needs a new build number. Bump APP_BUILD_NUMBER. Nothing you can do to reuse one.
The job never starts, no error No online node carries the label macos. Check Manage Jenkins → Nodes.
Flutter version mismatch The pipeline checks the SDK version exactly. Either change FLUTTER_VERSION or let FVM install the one that is written there.
pod: command not found CocoaPods is not installed on the Pipeline Mac, or brew is not in the agent's PATH. brew install cocoapods.

If the app has extensions

Widgets, push notification services and share extensions each need their own provisioning profile. Add a second entry to the provisioningProfiles map in the plist, and set the specifier per target — the plain PROVISIONING_PROFILE_SPECIFIER applies to every target and will pick the wrong one.

The one thing that comes back every year

The distribution certificate expires after twelve months. When it does:

  • Export a fresh dist.p12 on the Development Mac
  • Upload it over the old one in the bucket
  • Update ios-p12-password in Jenkins if you chose a new password

Nothing else changes. The API key does not expire, and the profile is downloaded fresh every build.

Two things to never do

  • Never log into Xcode on the Pipeline Mac. It creates its own certificates and quietly competes with the pipeline's.
  • Never create a new distribution certificate to fix a problem. You have two or three total for the whole company. Find the old one first.
Uses only tools that ship with macOS and Xcode — security, xcodebuild, xcrun, python3, openssl — plus FVM, CocoaPods and the AWS CLI, which the pipeline installs with Homebrew. No fastlane, no gems, no third-party signing tool.
