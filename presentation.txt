FLUTTER RELEASE PIPELINE - SLIDE CONTENT
========================================


============================================================
SLIDE 1 - INTRODUCTION
============================================================

  Flutter Release Pipeline
  Code to Play Store and TestFlight, with one button.


  What it is

  A Jenkins pipeline that takes our Flutter app from the Git repository
  all the way to the testers, without anybody doing the steps by hand.
  The developer only opens Jenkins, selects the platform, types the
  version and build number, and presses Build. Everything after that -
  cloning the code, bringing the secret files, generating code, building
  the release, and uploading it - is done by the pipeline.


  Where it runs

  On a dedicated Mac agent, so both Android and iOS builds come from the
  same machine, with the same tools, every single time.


  Why it matters

  A release is no longer one person's manual work. It is a process that
  anyone on the team can run, and it gives the same result every time.


============================================================
SLIDE 2 - PROBLEM
============================================================

  Earlier, giving a build meant one developer doing everything manually
  on his own laptop.


  1. Everything was manual

  He had to take the latest code, put the .env and the secret files in
  the correct places, run the build command, wait for it to finish, and
  then upload the file himself. For Android he opened the Play Console
  and uploaded the .aab. For iOS he opened Transporter and uploaded the
  .ipa. Then he typed the version name and release notes again by hand.
  Same steps, every release. And only he knew the full process, so when
  he was on leave, nobody else could give a build.


  2. Mistakes were found only at the end

  Many small things could go wrong - the .env was missing or from the
  wrong environment, the Flutter version on the laptop did not match the
  project, the keystore or google-services.json was old, or the build
  number was already used in Play Console. The problem was not the
  mistake, it was when we came to know about it. The build took around
  40 minutes, and the error appeared only at the last step. Fix one
  small thing and wait another 40 minutes.


  3. The whole release was slow

  Because everything was manual and the mistakes came late, one release
  easily took half a day. The testing team was waiting, the client was
  waiting, and the developer was just sitting and watching the build
  screen instead of doing his actual work.


  4. Uploading was a separate job of its own

  Even after the build was ready, it had to be uploaded by hand to two
  different places - Play Console internal testing for Android and
  TestFlight for iOS. Two websites, two logins, two sets of keys. If the
  developer forgot, a ready build simply stayed on his laptop while the
  testers kept waiting.


============================================================
SLIDE 3 - SOLUTION
============================================================

  One pipeline that does all five steps, in the same order, every time.


  Step 1 - Clone the repository

  Jenkins clones the branch from GitLab using a credential stored inside
  Jenkins, and prints the exact commit it is building. So we always know
  what went into a build, and no old code from somebody's laptop can get
  in.


  Step 2 - Bring the secret files

  The .env values are pulled from Infisical, and the files that cannot
  be committed - the keystore, google-services.json,
  GoogleService-Info.plist, the Play service account JSON and the Apple
  .p8 - are downloaded from S3 storage. Each file lands at its exact
  path in the project, and if any file comes down empty, the build stops
  right there. No secret ever sits on a laptop or appears in the logs.


  Step 3 - Generate the auto-generated code

  All the *.g.dart files are git-ignored, so a fresh clone does not have
  them and the app will not compile without this step. The pipeline runs
  easy_localization and build_runner, and it runs them after the .env is
  ready, because Envied reads that file. The order is fixed in the
  pipeline, so nobody can forget it or do it in the wrong sequence.


  Step 4 - Build with Flutter or Shorebird

  The developer chooses the runner. Flutter gives a normal release build
  (.aab or .ipa) and Shorebird gives a code push release. Both get the
  same flavour, entrypoint, version and build number. The exact Flutter
  SDK is installed and verified before the build starts, so the same
  commit always produces the same build. If no artifact is produced, the
  build is marked failed.


  Step 5 - Upload automatically

  Android goes to the Play internal testing track through fastlane
  supply, and iOS goes to TestFlight through Apple's xcrun altool. The
  release name and release notes can be sent from the same Jenkins
  screen. There is nothing left to upload by hand.


  And it works for any project

  The Jenkinsfile is exactly the same for every project. Only the
  pipeline.properties file changes - it holds the repository, the
  Flutter version, the secret file list and the store details. Onboarding
  a new app means writing one properties file, not building a new
  pipeline.
