The problem

Every release was done by hand

One developer, on one laptop, repeating the same steps for every build — and he was the only person who knew all of them.

PROBLEM 01

Everything was manual

Take the code, place the environment and secret files, run the build, wait, then upload the artifact and retype the version and notes.

PROBLEM 02

Mistakes surfaced last

A wrong environment, a mismatched Flutter version or a used build number only appeared after a forty-minute build, at the upload.

PROBLEM 03

The release was slow

Half a day per release. The testing team waited, the client waited, and the developer watched a build screen instead of working.

PROBLEM 04

Uploading was its own job

Play Console and TestFlight, by hand, with two logins and two sets of keys. Forget it and a finished build sits on a laptop.

The solution

Five steps, the same order, every time

01

Clone the repository

Clones the branch from GitLab with a credential stored in Jenkins and prints the exact commit. No stale code from a laptop gets in.

02

Bring the secret files

Environment values from Infisical; keystore, plists and store keys from object storage. Each lands at its exact path, never in a log.

03

Generate the generated code

Every generated Dart file is git-ignored, so a fresh clone has none of it. Runs after the environment file, because Envied reads it.

04

Build the release

Flutter for a normal build, Shorebird for a code push. The exact SDK is installed and verified first, so one commit gives one build.

05

Upload it automatically

fastlane sends the bundle to Play internal testing, altool sends the archive to TestFlight. Nothing is uploaded by hand.

The Jenkinsfile is identical for every project — only pipeline.properties changes: repository, Flutter version, secret file list and store identifiers. A new app is one properties file, not a new pipeline.
